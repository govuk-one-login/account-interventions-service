# Handover doc

This is a handover doc for a team taking over AIS. 
It covers what the service does, how the code is arranged, and what is deployed. 
Local setup, build commands and manual deploy steps are in the root [README](../README.md) and are not repeated here.

## What the service does

AIS is the system of record for account interventions in GOV.UK One Login.
A fraud analyst (or an automated process) decides an account should be suspended, blocked, or forced to reset its password or reprove its identity.
That decision reaches AIS as an event.
AIS applies it to the account, stores the resulting state, and exposes that state to relying parties — mainly Authentication, Orchestration and IPV Core — which use it to decide whether a user may sign in and what they must do first.

Interventions are a state machine so not every event is valid in every state, and invalid transitions are rejected and audited.
Events arrive from and audit events are emitted to TxMA as standard.

## Event flow

```
TxMA ──> TxMAIngressQueue ──> TxmaEventHandlerFunction (fan-out by event_name)
                                 │
                 AUTH_DELETE_ACCOUNT│            everything else
                                 ▼                      ▼
                   AccountDeletionEventQueue   AccountInterventionEventsQueue
                                 │                      │
                                 ▼                      ▼
                 AccountDeletionProcessor      InterventionsProcessor
                                 │                      │
                                 ▼                      ▼
                        AccountStatusTable  ◄────────────┤
                                            InterventionEventsTable
                                                         │
                                                         ▼
                                              TxMAEgressQueue ──> TxMA (audit)

Relying parties ──(VPC endpoint)──> PrivateApi ──> StatusRetrieverFunction ──> tables
```

`InterventionsProcessor` is the main entrypoint to the service.
For each message it validates the event, reads the current account state, asks the state engine whether the transition is allowed, writes the new state, emits an audit event, and appends to the event history.
Validation failures and disallowed transitions are audited and dropped rather than retried.

## The state machine

`src/services/account-states/config.ts` is a directed graph: six account states (nodes), intervention codes (edges), and an adjacency list declaring which codes are permitted from each state.
`account-state-engine.ts` applies it.

| State | blocked | suspended | resetPassword | reproveIdentity |
| --- | --- | --- | --- | --- |
| `AccountIsOkay` | – | – | – | – |
| `AccountIsSuspended` | – | ✓ | – | – |
| `AccountIsBlocked` | ✓ | – | – | – |
| `AccountNeedsPasswordReset` | – | ✓ | ✓ | – |
| `AccountNeedsIdReset` | – | ✓ | – | ✓ |
| `AccountNeedsPswAndIdReset` | – | ✓ | ✓ | ✓ |

Codes `C01`–`C07` are fraud interventions (suspend, unsuspend, block, force password reset, force ID reverification, force both, unblock).
`C90`–`C95` are user-action events from Authentication and IPV that clear an intervention once the user has done what was asked.
A blocked account only accepts `C07` (unblock).

Changing this config changes production behaviour for every account.
Treat it as the highest-risk file in the repo; there is a dedicated alarm (`AccountStateEngineConfigurationIssue`) for when it is inconsistent.

## Code layout

| Path | Purpose |
| --- | --- |
| `src/handlers/` | Lambda entry points. Each `*-handler.ts` wires dependencies; the matching `*.ts` holds the logic and is unit-tested in isolation. |
| `src/services/` | Business logic — state engine, event validation, persistence, audit, config, feature flags, JWT verification. |
| `src/tables/` | DynamoDB access. Each table has a Zod schema, an interface, a persistent implementation and an in-memory implementation for tests. |
| `src/data-types/` | Constants, enums, errors, API request/response schemas (v1 and v2). |
| `src/commons/` | Logger, tracer, metrics (AWS Lambda Powertools), shared helpers. |
| `src/frontend/` | Fastify app serving the internal web UI, with Nunjucks views. |
| `src/specs/` | OpenAPI. `api.yaml` is the legacy v1 API; `main.yaml` is the current multi-version API and is generated by `npm run generate:spec:main`. |
| `src/infra/` | The four SAM templates. |
| `packages/ais-status-sdk/` | Published TypeScript client (`@govuk-one-login/ais-status-sdk`) that relying parties — and the AIS frontend itself — use to call the status API. |
| `adr/` | Architecture decision records. Read these before changing structure. |
| `docs/incidents/` | Post-incident notes. Short and worth reading in full. |

The handler/logic split and the interface-plus-in-memory-implementation pattern are deliberate (see ADR 004 on composition over inheritance and ADR 005 on no runtime patching in tests).
Follow them; the tests depend on them.

## Lambdas

All run Node 24 on arm64 with X-Ray tracing and a Dynatrace layer, inside the VPC on protected subnets.

| Function | Trigger | Does |
| --- | --- | --- |
| `TxmaEventHandlerFunction` | `TxMAIngressQueue` | Routes TxMA messages to the deletion or intervention queue by `event_name`. |
| `InterventionsProcessorFunction` | `AccountInterventionEventsQueue` | Validates and applies interventions; writes state and history; emits audit events. |
| `AccountDeletionProcessorFunction` | `AccountDeletionEventQueue` | Marks the account deleted and sets a TTL for retention expiry. |
| `StatusRetrieverFunction` | `PrivateApi` / `PrivateRestApi` | Serves the status and history endpoints. |
| `FrontendFunction` | FAI API Gateway (cross-account) | Serves the internal web UI. Separate stack. |
| `InvokePrivateAPIGatewayFunction` | Manual | Test utility — lets you call the private API from inside the VPC. Usage in the README. |
| `TtlBackfillFunction` | Manual | One-off utility to backfill TTLs onto `intervention-events` rows. Non-production only. |

All SQS-triggered functions use `BatchSize: 1` with `ReportBatchItemFailures`.
All queues have a DLQ at `maxReceiveCount: 60`.
That number is high on purpose — see incident 001 on Lambda retries.

## Data model

Two DynamoDB tables, both pay-per-request, both encrypted with a customer-managed KMS key, both with point-in-time recovery, TTL on a `ttl` attribute, deletion protection outside dev, and a `BackupFrequency: Bihourly` tag.
Neither has a GSI or a stream.

**`<core-stack>-account-status`** — current state, one item per user.
Partition key `pk` (the user's pairwise subject ID).
Holds the four state booleans, the intervention name, `sentAt` / `appliedAt` / `updatedAt`, the `history` string array, `isAccountDeleted` with `deletedAt`, and `auditLevel`.

**`<core-stack>-intervention-events`** — append-only event history.
Partition key `accountId`, sort key `createdAt`.
One item per event, with reason, requester, originating component and TTL provenance (`ttlSource`).

The split exists so that reads on the sign-in path are a single `GetItem` against a small item, while full history is a separate query.
`src/commons/history-string-builder.ts` encodes and decodes the legacy packed `history` strings on the status table; the events table is the successor.
Background in `docs/design-docs/persisting-interventions.md` and `docs/internal-docs/account-status-history.md`.

## APIs

The status API is **private**: `EndpointConfiguration: PRIVATE`, reachable only through VPC endpoints, with a resource policy that denies any request whose `aws:SourceVpc` is not in the environment's allow-list.
Those VPC and VPC-endpoint ID lists are hardcoded per environment in the `EnvConfig` mapping in `src/infra/main/template.yaml`.
**Onboarding a new consumer means editing that mapping and redeploying** — there is no dynamic registration.

There are two API Gateways in the main stack for version-migration reasons:

| Gateway | Stage | Spec | Endpoints |
| --- | --- | --- | --- |
| `PrivateRestApi` | `v1` (parameterised) | `src/specs/api.yaml` | `GET /ais/{userId}` |
| `PrivateApi` | `main` | `src/specs/main.yaml` | `GET /v1/ais/{userId}`, `GET /v2/ais/{userId}`, `GET /v2/ais/{userId}/history` |

`StatusRetrieverFunction` serves all of them and branches on `event.resource`.
v1 returns the raw state booleans plus intervention metadata; v2 returns a list of named active interventions and is the version new consumers should use.
v2 reads `x-client-id` and `x-sdk-version` headers for attribution metrics — encourage consumers to send them via the SDK.

## Infrastructure — four stacks

Split by lifecycle: data outlives application code, and alarms should be deployable without touching either.

| Stack | Template | Contains |
| --- | --- | --- |
| `ais-core` | `src/infra/core/template.yaml` | The two DynamoDB tables and their KMS keys. Deployed rarely. Exports table names and ARNs. |
| `ais-main` | `src/infra/main/template.yaml` | Everything else: Lambdas, IAM, four SQS queues plus DLQs, three KMS keys, both API Gateways, log groups, CSLS subscription filters, CodeDeploy canaries, SSM parameters. ~83KB and the file you will spend most time in. |
| `ais-alarm` | `src/infra/alarm/template.yaml` | ~60 CloudWatch alarms. No other resources. |
| `ais-frontend` | `src/infra/frontend/template.yaml` | The frontend Lambda and its own KMS keys and log groups. |

`ais-main` imports VPC values from a `VpcStackName` stack and table details from `CoreStackName`.
Deploy order is core → main → alarm/frontend.

### Queues

| Queue | Producer | Consumer |
| --- | --- | --- |
| `TxMAIngressQueue` | TxMA (external account in staging and above; internal queue in dev/build) | `TxmaEventHandlerFunction` |
| `AccountInterventionEventsQueue` | `TxmaEventHandlerFunction` | `InterventionsProcessorFunction` |
| `AccountDeletionEventQueue` | `TxmaEventHandlerFunction` | `AccountDeletionProcessorFunction` |
| `TxMAEgressQueue` | all processors | TxMA |

In dev and build (`IsInternal`) AIS owns the ingress queue so you can inject test events.
From staging up it subscribes to a TxMA-owned queue in the TxMA account, whose ARN and KMS key ARN are in the `EnvConfig` mapping.

### Frontend and its authentication

ADR 10 covers this in more detail.
The frontend Lambda runs in the AIS account but is invoked by the Fraud Admin Interface (FAI) API Gateway in the FAI AWS account, which forwards the `/interventions` subpath.
FAI performs authentication and passes a JWT in the authoriser context; `src/frontend/authoriser.ts` verifies it against an FAI-owned KMS key (`FaiAuthSigningKeyArn`, mapped per environment).
Cookies are namespaced `ais_` to stay isolated from FAI's.

Consequences worth knowing:

- The `FrontendApi` resource in the template is behind the VPN but is unauthenticated, which is why it is
  gated behind `IsGatewayEnabled` — `EnableGateway=true` *and* `Environment=dev`. It is a local
  development convenience so do not enable it elsewhere.
- `DISABLE_AUTH` swaps in `StubAuthoriser`, which accepts everything. It must stay `false` outside
  dev.
- A change to FAI's authoriser can break AIS's frontend. This is called out as a known consequence
  in ADR 010.

## Configuration

There are three configuration mechanisms, all resolved at cold start:

1. **Environment variables** via `AppConfigService` (`src/services/app-config-service.ts`). A
   single `CONFIG_ENVIRONMENT_MAPPING` declares each value's env var, type (`string` / `number` /
   `url`) and whether it is optional. Required values throw `InvalidEnvironmentVariableError` on
   startup. Add new config there, not ad hoc. Incident 003 was caused by config read at the wrong
   point in the lifecycle.
2. **Feature flags** via `FeatureFlagsFromEnvironmentVariables` (`src/services/feature-flags.ts`).
   Currently `aisFrontend`, `aisSendTxMA`, `disableAuth`, `bypassInterventionEventsTable`. Values
   come from the `FeatureFlags` mapping in the templates.
3. **CloudFormation `EnvConfig` mappings** for per-environment values that are not secrets: log
   level, TxMA account ID and queue ARNs, SNS topic ARNs, VPC and VPC-endpoint allow-lists,
   Dynatrace secret ARN, FAI account ID and signing key.

Dynatrace credentials are the only runtime secrets, resolved from Secrets Manager at deploy time via `{{resolve:secretsmanager:...}}`.

## Observability

Structured logging, metrics and tracing all come from AWS Lambda Powertools (`src/commons/`).
Metric names are enumerated in `src/data-types/constants.ts` (`MetricNames`) and are what the alarms key off — renaming one silently breaks an alarm.

Logs go to CloudWatch and are shipped to CSLS via subscription filters on every log group.
Dynatrace receives traces through the Lambda layer.
Logs containing user identifiers are prefixed `LOGS_PREFIX_SENSITIVE_INFO`; keep using that marker.

`ais-alarm` covers queue depth and age (tiered warning/critical), DLQ depth, Lambda errors and throttles over 1/5/10 minute windows, API 4xx/5xx and p80/p95 latency, TxMA publish failures and latency, DB query errors, and business-level conditions such as `InterventionNotAllowed`, `InterventionEventStale`, `AccountMarkedAsDeleted` and `AccountStateEngineConfigurationIssue`.
Alarms carry a `RunBookURL` and a `TeamManualPlaybookUrl`; those links are the operational runbook and are set in `samconfig.toml`.

`ais-main` also defines CodeDeploy canary alarms that automatically roll back a Lambda deployment on errors from the status retriever, interventions processor, deletion processor, or TxMA publishing.

## Environments and deployment

Deployment of AIS follows the GDS Dev Platform secure pipelines pattern.
On merge to `main`, the relevant `merge-*-to-main.yaml` workflow validates the template, runs the acceptance checks, builds with `sam build`, and uploads a signed artifact to an S3 artifact bucket using `govuk-one-login/devplatform-upload-action`.
AWS CodeDeploy picks the artifact up and promotes it through the environments.
The pipelines themselves are provisioned by the `sam-pipelines` Terraform stack in `ais-base-infrastructure`.

Each stack has its own workflow trio — `validate-*`, `merge-*-to-main`, `manual-publish-*-to-dev` — so stacks are released independently.
`manual-publish-*-to-dev` is also a direct route to pushing a branch to dev.

`ais-base-infrastructure` uses Terraform with per-environment directories under `terraform/env/` (`*.tfvars` plus `*.backend.hcl` for remote state) and two stacks: `base-stacks` (Dev Platform account provisioning) and `sam-pipelines`.

## Testing

| Tier | Command | Notes |
| --- | --- | --- |
| Unit | `npm run test:unit` | Vitest with coverage. The bulk of the suite. Uses the in-memory table services. |
| Types | `npm run test:types` | `tsc --noEmit`. |
| DynamoDB Local | `npm run test:unit:dynamodb-local` | Needs the Docker container started first. Tagged and skipped by default; separate config file. |
| Contract (Pact) | `npm run test:pact:provider` / `:consumer` | AIS is provider for the status API and consumer of TxMA events. Published to a Pact broker by dedicated workflows. See ADR 007. |
| Mutation | `npm run test:mutation` | Stryker, with a score ratchet in `.ratchet/mutation.score.json` enforced on PRs. |
| Feature (API) | `feature-tests/` | Vitest + Supertest + Cucumber against a deployed environment. Needs AWS credentials and `SAM_STACK_NAME`. |
| Feature (UI) | `feature-tests-ui/` | Playwright against the frontend. |

Quality gates on PRs: acceptance checks (build, lint, types, unit, DynamoDB Local, SonarCloud), mutation ratchet, SHA-pinned-actions check, pre-commit hooks, gitlint commit message rules, and branch protection rulesets in `.github/rulesets/`.

Lint covers three things: ESLint for TypeScript, `sam validate --lint` for every template, and Spectral for the OpenAPI specs.
